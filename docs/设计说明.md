## 1. 需求与范围

### 1.1 场景

输入一个主题（如「向量数据库的现状与趋势」），三个 Agent 协作产出一期语音播报，
最终回复包含**核心要点 / 语音播报 / 口播稿 / 参考来源**四部分，并附一段**真实合成的音频**。

### 1.2 硬性约束的落地方式

| 约束 | 实现 |
| --- | --- |
| ≥3 个 agent（或 ≥3 个 pipeline 节点） | supervisor + researcher + writer + voice + finish，共 5 个节点 |
| ≥2 种能力来源 | 联网搜索（工具）、语音合成（工具）、三种不同人设的 LLM 节点 |
| 产物含非纯文本 | 千问 TTS 生成 `.wav`，前端 `<audio>` 播放 |
| 必须新增一个工具协议 | `qwen_tts`（见第 4 节） |
| 禁止 mock | 全部走真实服务：DeepSeek / 博查 / 千问 TTS |
| 配置纪律 | 密钥只在 `.env`，配置加载时强制校验（见第 5 节） |

### 1.3 明确不做的事

- 不做图片/视频产物（场景聚焦"调研 + 播报"，避免摊薄）
- 不接 Langfuse（用 JSONL + trace_id 满足"链路可复核"）
- 不做鉴权限流（属加分项，与主链路无关）

```

                    │ 后台任务
┌───────────────────▼──────────────────────────┐
│ graph/          LangGraph supervisor 编排     │
│                 state / nodes / build / runner│
└───────┬──────────────────────────────┬────────┘
        │                              │
┌───────▼──────────┐        ┌──────────▼────────┐
```

**分层的意义**：`graph/` 只关心"下一步谁干"；`tools/` 只关心"怎么跟外部服务说话"；
`api/` 只关心"怎么把状态暴露给浏览器"。三者互不知道对方的内部细节。

## 3. 编排层设计

### 3.1 为什么是 supervisor

三个 worker 之间有**强阶段依赖**：没有资料写不了稿，没有稿配不了音。

- **pipeline**：顺序固定，但一旦 TTS 失败就整条链路崩，无法"降级交付文字稿"；
- **network**：worker 互相转交，谁该在什么时候接手全靠模型自觉，日志难读、容易来回踢皮球；
- **supervisor**：把"下一步"收敛到一个节点，规则显式、可加日志、可加兜底。

### 3.2 状态设计

`AgentState` 把两类东西分开：

```python
# 业务产物
sources / notes / script / audio / artifacts / answer_md
# 调度信号
next_worker / turns / stage / audio_attempts
```

把调度信号也放进状态，是 supervisor 模式的关键——
**调度决策因此可观测、可回放**，而不是藏在某个 `if` 里。

### 3.3 终止条件

三层保险，任何一层都能结束：

1. 产物齐备 → `finish`
2. `turns > max_turns`（默认 10）→ `finish`
3. LangGraph 的 `recursion_limit=60` 兜底，防止图跑飞

`voice` 节点用 `audio_attempts` 记录尝试次数，超过 2 次就跳过配音、降级交付文字稿。

### 3.4 每个 worker 的输入输出

| 节点 | 输入 | 输出 |
| --- | --- | --- |
| `supervisor` | 全量状态 | `next_worker` / `turns` |
| `researcher` | `query` | `search_queries` / `sources` / `notes` |
| `writer` | `notes` + `query` | `script` |
| `voice` | `script` | `audio` / `artifacts` |
| `finish` | 全部产物 | `answer_md` |

worker 之间**不直接传值**，一律通过状态。这样任何一步重试都不会污染其他节点。

## 4. 工具协议层设计

### 4.1 模板方法：把协议差异压到两个函数

```python
async def call(self, **kwargs) -> ToolResult:      # 基类，子类不覆盖
    spec = self._build_request(**kwargs)            # ← 子类实现
    response = await self._send(client, spec)       # 基类：鉴权/超时/状态码/脱敏
    return await self._parse_response(response, **kwargs)  # ← 子类实现
```

`_send()` 负责的事：

- 按 `api_key_env` 从环境变量取 Key，注入 `Authorization: Bearer …`
- 统一超时
- 非 2xx 抛 `ToolError`，错误摘要过 `sanitize()`
- 缺 Key 时给出"请在 .env 配置"的明确提示，而不是让上游返回 401

**收益**：新增一种协议的成本 ≈ 60 行，且不会漏掉鉴权或脱敏。

### 4.2 已实现的三种协议

| 协议名 | 类 | 特点 |
| --- | --- | --- |
| `bocha` | `BochaSearchClient` | POST + JSON，`data.webPages.value[]` |
| `readability` | `ReadabilityClient` | GET + trafilatura 抽正文，无需鉴权 |
| `qwen_tts` ★ | `QwenTTSClient` | **本组新增**，非 OpenAI 协议，见下 |

### 4.3 千问 TTS 协议详解（重点）

**它和 OpenAI TTS 的三处不同：**

| | OpenAI `/v1/audio/speech` | 千问 `qwen3-tts-flash` |
| --- | --- | --- |
| 端点 | `/v1/audio/speech` | `/api/v1/services/aigc/multimodal-generation/generation` |
| 请求体 | `{model, input, voice}` | `{model, input:{text, voice, language_type}}` |
| 返回 | 二进制音频流 | JSON，音频在 `output.audio.url`（24h 有效 OSS 链接） |

**因此 `_parse_response` 必须多做两件事：**

```python
audio_url = payload["output"]["audio"]["url"]
raw = await self._fetch_bytes(audio_url, self.app.app.max_audio_bytes)  # ① 二次下载
dest.write_bytes(raw)                                                   # ② 落盘
return ToolResult(ok=True, artifacts=[Artifact(kind="audio", url=f"/files/{dest.name}", ...)])
```

**三个容易踩的点，均已处理：**

1. **流式 + 硬上限**
   `_fetch_bytes()` 每 64KB 检查一次累计大小，超 `MAX_AUDIO_BYTES`（默认 8MB）立即中止。
   直接 `response.content` 会把上游的任意大小读进内存。

2. **签名不外泄**
   - 下载走**独立通道**，不带 `Authorization`（签名链接不需要也不该带）
   - `sanitize()` 抹掉 `sk-*` / `Bearer *` / `Signature=` / `OSSAccessKeyId=`
   - 带签名的原始 URL **从不**写日志、从不返回前端；日志里显示 `oss://…(已隐藏签名)`

3. **Markdown 先清洗再合成**
   `plain_text()` 去掉 `##`、`**`、`[1]`、列表符号——否则 TTS 会把它们念出来。
   超长文本按 `max_text_chars` 截断，并尽量截在句号处。

### 4.4 注册机制

```python
@register                                  # tools/qwen_tts.py
class QwenTTSClient(ToolClient):
    protocol = "qwen_tts"
```

```yaml
# config.yaml
tools:
  qwen_tts:
    protocol: qwen_tts        # ← 与代码里的 protocol 对应
    enabled: true
```

业务代码只按**工具名**调用（`self.tools["qwen_tts"]`），完全不感知协议。

## 5. 配置与密钥管理

### 5.1 三层结构

```
config.yaml   业务编排（agent / tools / graph），不含任何密钥
.env          密钥（gitignore）
环境变量      运行时覆盖（优先级最高）
```

`${VAR}` 与 `${VAR:-默认值}` 在加载时插值，所以 `LLM_BASE_URL` 不配置也能跑（用默认 DeepSeek 端点）。

### 5.2 密钥硬校验

`config.py::_assert_no_secrets()` 在**解析后、实例化前**扫描整棵配置树：

```python
if _LOOKS_LIKE_SECRET.match(value):     # sk-xxxx / 40 位以上随机串
    raise ValueError("配置项 xxx 看起来是密钥明文…")
if value == os.environ.get(env_name):   # 把 Key 换个字段名藏起来也拦得住
    raise ValueError("配置项 xxx 的值与环境变量 DEEPSEEK_API_KEY 完全相同…")
```

**这是一条硬失败**：写错了服务起不来，不会"带病运行"。

## 6. 可观测性设计

### 6.1 trace_id 贯穿

`POST /chat` 生成 `trace_id`（16 位 hex），同时：

- 通过响应返回给前端（界面固定展示、可复制）
- 写进每一条日志
- 存在 `RunRecord` 里供轮询接口返回

### 6.2 日志格式（JSON Lines）

```json
{"ts":"2026-10-21T14:20:11.482+08:00","trace_id":"79fb2362395a4399","session_id":"8e83e7b33606",
 "span":"supervisor","event":"decision","duration_ms":null,
 "detail":{"turn":3,"next":"voice","reason":"还没有音频产物","has_notes":true,"has_script":true,"has_audio":false}}
```

### 6.3 四层 span

```
run              一次请求
├─ supervisor     调度决策（含 reason）
├─ node:xxx       节点耗时
│  ├─ llm:xxx     llm_call / llm_result（含 token 数、输出预览）
│  └─ tool:xxx    start / end（含耗时、产物、摘要）
```

复核方式（录屏③可直接演示）：

```bash
curl "http://127.0.0.1:8010/logs?trace_id=<界面上的 trace_id>"
# 或
grep 79fb2362395a4399 logs/agent.log
```

### 6.4 脱敏

所有日志字段进 `_clean()` 递归过一遍 `sanitize()`，防止上游报错把 Key 带进日志。

## 7. 接口设计

### 7.1 为什么是「提交 + 轮询」

单次生成 40–90 秒：

- 长连接（或同步请求）容易在演示时超时、白屏
- 更重要的：**没法展示阶段进展**

所以 `POST /chat` 只做三件事（生成 id、登记记录、丢后台任务）就立即返回；
前端每 900ms 轮询一次 `GET /chat/{trace_id}`，把 `stage` 渲染成进度条。

### 7.2 错误设计

| 场景 | 状态码 | 前端表现 |
| --- | --- | --- |
| 消息为空 | 422（Pydantic） | "请求参数不合法：message 不能为空" |
| trace 不存在 | 404 | "找不到记录：服务可能已重启" |
| 上游失败 / 超时 | 任务内 `status=error` | "生成失败：<脱敏后的原因>" |
| 未捕获异常 | 500（兜底 handler） | "服务端错误：…" |

关键点：**任何路径都不会白屏**，也不会把 Key 泄进错误框。

## 8. 前端设计

| 需求 | 实现 |
| --- | --- |
| 多轮 | `localStorage` 存 `session_id`，每轮携带；后端保留最近 6 轮 |
| Markdown | 后端 `markdown-it-py` 渲染成 HTML，前端直接插入（省一个前端依赖） |
| 音频 | `artifacts[]` 驱动，`kind==="audio"` 渲染 `<audio controls>` |
| trace_id | 顶栏固定展示 + 复制按钮 |
| 调用链 | 折叠面板展示最近 18 条事件（span / event / 耗时） |
| 错误 | 统一 `explainError(status, data)`，把 `detail` 翻成中文 |

## 9. 关键取舍与踩坑

1. **TTS 返回的是链接，不是流**
   一开始按 OpenAI 的思路写（直接读 `response.content`）会拿到 JSON 文本而不是音频。
   正确做法是一次额外的流式下载。

2. **不流式下载会 OOM**
   音频动辄 5MB，上游若异常返回大文件，`response.content` 会整块进内存。
   改成 `stream()` + 累计大小检查。

3. **签名 URL 是最容易泄密的入口**
   报错信息里经常带完整 URL。所以 `sanitize()` 必须覆盖 `Signature=` / `OSSAccessKeyId=`。

4. **长任务不能用同步请求**
   最早想一次请求返回结果，结果浏览器端等 60 秒体验极差且易断。
   改成提交 + 轮询后，进度可视化，演示也稳。

5. **supervisor 的规则要能解释**
   如果把调度交给 LLM 自己判断，演示时很难说清"为什么第 3 轮去配音"。
   本项目用规则驱动（`config.graph.llm_routing=false`），并在日志里写明 reason。
